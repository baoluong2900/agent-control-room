## 1. Bug đã tìm và sửa: run bị "vô hình" trong lúc spawn

### Triệu chứng

`npm test` đang **fail 1 test**, reproducible (chạy lại 3 lần đều fail — không flaky):

```
not ok — agent starts beyond the concurrency limit stay queued until a slot opens
  tests/agent-process-lifecycle.test.ts:98
  Expected values to be strictly equal:  2 !== 3
```

### Root cause

Tại `src/main/processes/agent-process-manager.ts`, `drainQueue()` shift một run ra
khỏi `queued` rồi `await spawnQueued()`. Nhưng `spawnQueued()` phải `await
buildInvocation()` **trước khi** đăng ký child vào `running`.

Trong khoảng thời gian đó run không nằm trong `queued` cũng không nằm trong
`running` — nó vô hình với toàn bộ manager. Ba hệ quả thật:

| # | Hệ quả | Vì sao |
| --- | --- | --- |
| 1 | Vượt giới hạn concurrency | Gate dùng `running.size`, run đang spawn không được tính, nên process thứ 4 vẫn spawn được dù `MAX_CONCURRENT_RUNS = 3` |
| 2 | UI mất session | `sessions()` chỉ đọc `running` + `queued`, nên agent biến mất khỏi bảng rồi xuất hiện lại |
| 3 | **Stop không có tác dụng + orphan process** | `stop()` tìm trong `queued` và `running` đều không thấy → return im lặng. Process spawn ra sau đó không ai quản lý, chạy mãi |

Bằng chứng từ script debug (state thật ngay sau `stop(runs[0])`):

```
sessions(): [ 5330b1 planning, 1cea55 queued ]        ← chỉ 2 entry
db:         [ 5330b1 planning, 8e661c queued,
              1cea55 queued,   60ebc1 stopped ]        ← 8e661c ở đâu?
```

`8e661c` đã bị shift khỏi `queued` nhưng chưa vào `running` → không xuất hiện trong
`sessions()`, không chiếm slot, `stop()` không thấy.

### Fix đã áp dụng

Cùng một file, 4 điểm:

1. **Thêm `spawning: Map<string, QueuedProcess>`** — giữ các run đang trong quá
   trình spawn, để chúng không còn vô hình.
2. **`activeCount() = running.size + spawning.size`** — concurrency gate trong
   `drainQueue()` dùng hàm này thay cho `running.size`, nên spawn đang bay vẫn
   chiếm slot.
3. **`sessions()` báo cáo run đang spawn** với status `planning` và command
   `(starting)`, nên UI không mất session.
4. **`stop()` xử lý được run đang spawn**: ghi `stopped` vào DB, emit event, và
   thêm runId vào `cancelledSpawns`. `spawnQueued()` kiểm tra cờ này **ngay sau khi
   có child handle** và SIGTERM luôn thay vì publish nó như live → không còn
   orphan process.

### P0 — UI hứa nhiều hơn runtime

**2.1 Remote workflow triggers vẫn không có runner**

- `src/main/workflows/` chỉ có `step-context.ts`, `workflow-schedule.ts`,
  `workflow-scheduler.ts`, `workflow-seeds.ts`, `workflow-service.ts` — không có
  listener, poller, hay HTTP service nào.
- `git-push` / `issue-created` / `webhook` có trong contract
  (`src/contracts/workflow.ts:23-26`) và trong UI metadata
  (`src/renderer/workflows/workflow-ui.ts:46-49`).
- Đang được gate + warn đúng cách (`workflow-ui.ts:57-59`).
- **Còn sót:** `src/main/workflows/workflow-seeds.ts:108` seed workflow với
  `trigger: { type: "git-push" }` và `:180` với `type: "issue-created"` — seed data
  vẫn quảng cáo trigger không chạy được.

Việc nên làm: đổi seed sang `manual`/`schedule`, và giữ remote trigger disabled tới
khi có ref polling / API polling / local webhook listener thật.

**2.2 OAuth/device chưa phải auth flow thật**

  `this.linkOpener.openExternal(url)` rồi `return { provider, opened: true, url }`.
- Không có callback listener, không device-code exchange, không token refresh,
  không xử lý expiry.
- Contract vẫn khai `ProviderConnectionAuthMode = "oauth" | "device" | "api-key"`.

Việc nên làm: hoặc đổi copy thành "Open provider login/docs" và coi connection là
metadata + secret thủ công, hoặc implement callback/deep-link + device-code polling
+ token exchange + refresh.

## 3. Những phần đã kiểm tra và chạy thật

Không nên gọi các mục này là "chưa làm":

- IPC bridge khớp contract cho toàn bộ API hiện có (`system`, `projects`,
  `settings`, `agents`, `tasks`, `workflows`, `git`, `knowledge`).
- Agent process lifecycle: spawn, stdin `send()`, restart, concurrency queue,
  preflight executable check, terminal log retention có bound.
- Workflow run + approval gate park/resume; schedule runner parse được `Daily`,
  `Weekly`, `Monthly`, `Every N minutes/hours`; `file-change` có local runner với
  debounce/ignore/self-loop protection.
- Workflow step chaining: `{{previous.output}}` và `{{steps.<id|name>.output}}`, sống
  sót qua approval gate.
- Step nhận credential thật qua `resolveProviderEnv()`; provider connection có
  `baseUrl` để trỏ tới proxy/router.
- Provider secret encrypted bằng Electron `safeStorage`, SQLite chỉ lưu
  `tokenReference`.
- App DB có `schema_migrations` với runner transactional + idempotent.
- Task retry policy, workflow metrics delta, knowledge truncation report,
  diagnostics tiers, structured chat capability flags — đều đã land.
